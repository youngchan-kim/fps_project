디자인 패턴
디자인 패턴은 객체지향 프로그래밍 설계중 자주 발생하는 문제를 피하기 위해 사용
문제 해결을 위해 사용한 코드의 기법들
알고리즘이 아니다. 설계방법을 정리한 코딩 방법론
팀 프로젝트시 의사소통의 수단

특징 개발중 새로운 기능 추가시 변수발생 최소화

주의점
모든 문제는 디자인 패턴만으로 해결할 수 없음
코드베이스의 간결성이 중요
특정 패턴을 사용할 때 해당 패턴이 왜 효율적인 방식인지 이해가 중요

-싱글톤 패턴
하나의 프로그램에 특정인스턴스를 하나만 사용해야하는 경우
하나의 인스턴스만 있는 것을 보장 가능
불필요한 메모리 낭비를 최소화한다.
생성자를 클래스 내부에서만 사용할 수 있도록 반드시 private 접근한정자를 통해 제한

-옵저버 패턴 
관찰대상의 상태가 갱신되면 모든 관찰자들은 갱신된 내용을 알고 자신의 상태를 갱신한다.
1대 다수의 관계를 가짐

전달 방식 
push : 관찰대상자에서 관차자에게 갱신된 데이터를 보내는 방식
관찰대상자가 갱신된 데이터를 보내야 관찰자가 알수 있음
관찰자에게 정보를 입력해주거나 제거하고 수정할 수 있음
pull : 관찰자가 관찰 대상자에게서 갱신된 데이터를 가져오는 방식
관찰자가 가져오고자 할대 데이터를 가져올수있음

-컴포지트 패턴 
사용자가 단일 객체와 복합 객체 모두 동일하게 다루도록 한다.
트리구조로 구성
부분 -전체 계층으로 표현


component는 부분과 전체에 대한 통합 인터페이스

Leaf는 부분으로 component와 일반화 관계에 있음 인터페이스를 객체화한 개별 객체임

composite이 전체 component가 부분인 집합관계
composite는 트리구조로 0개 이상의 component를 가지며 관리

부모인 composite의 기능을 가진 자식인  component를 객체화한 Leaf

-팩토리 패턴
팩토리 메소드

생성 후 해야할 일의 공통점을 정의
한종류의 객체만을 생성

Creator는 객체 생성 팩도리 메소드를 가지는 인터페이스이다.

ConcreteCreator는 인스턴화됨

-추상 팩토리 패턴 
추상팩토리는
많은 수의 연관된 서브 클래스를 특정 그룹으로 묶어 한번에 교체한다.
연관 또는 독립된 객체들을 생성할 인터페이스를 지닌다.
생성해야 할 객체의 공통점에 유의 : 예시 ) 아머와 무기가 있을때 대검을 아머로 잘못 만든경우를 유의
한번에 여러 종류의 객체를 생성

-스트래티지 패턴 
예시 : 모든 직업에 스킬, 무브 함수가 있을때 사용할 스킬의 클래스를 포인터로 주소를 불러와 사용한다.
클래스의 객체를 매번 소멸생성하지 않도록 한번 생성후  클래스자체가 소멸되지 않는한 계속 생성할 수 있도록함?
